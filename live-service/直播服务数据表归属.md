# 直播服务数据表归属

## 一、归属结论

直播服务独占并维护以下三张表：

| 表名 | 所属微服务 | 领域用途 | 写入方 | 读取方 |
| --- | --- | --- | --- | --- |
| `live_room` | 直播服务 | 直播间、主播、推拉流地址和直播状态 | 直播服务 | 直播服务；其他服务通过 HTTP API 获取 |
| `live_danmu` | 直播服务 | 直播间弹幕历史 | 直播服务 | 直播服务；其他服务通过 HTTP API 获取 |
| `room_likes` | 直播服务 | 直播间累计点赞数 | 直播服务 | 直播服务；其他服务通过 HTTP API/WebSocket 获取 |

其他微服务不得直接连接并修改这三张表。需要直播信息时，应调用直播服务接口或订阅后续定义的领域事件。

## 二、`live_room` 直播间主表

### 表结构

| 字段 | 类型 | 约束/默认值 | 说明 |
| --- | --- | --- | --- |
| `id` | `BIGINT` | 主键、自增 | 直播间 ID |
| `user_id` | `BIGINT` | `NOT NULL` | 主播用户 ID；逻辑关联用户中心，不建立跨库外键 |
| `category_id` | `BIGINT` | 可为空 | 分类 ID；逻辑关联分类服务，不建立跨库外键 |
| `title` | `VARCHAR(100)` | `NOT NULL` | 直播间标题 |
| `stream_name` | `VARCHAR(100)` | `NOT NULL UNIQUE` | SRS 流名称 |
| `push_url` | `VARCHAR(500)` | `NOT NULL` | 主播端推流地址 |
| `play_url` | `VARCHAR(500)` | `NOT NULL` | 默认播放地址 |
| `cover_url` | `VARCHAR(500)` | 可为空 | 直播间封面地址 |
| `status` | `VARCHAR(20)` | `NOT NULL`，默认 `offline` | 当前状态；现有代码使用 `online`、`offline` |
| `create_time` | `TIMESTAMP` | `NOT NULL`，默认当前时间 | 创建时间 |

### 访问关系

| 操作 | 触发接口/代码 | 说明 |
| --- | --- | --- |
| 新增 | `POST /api/live/rooms` | 保存主播、标题和 SRS 推拉流地址，创建后状态为 `online` |
| 查询列表 | `GET /api/live/rooms` | 只查询 `status = 'online'` 的直播间，支持分类、分页 |
| 查询详情 | `GET /api/live/rooms/{roomId}` | 返回直播间详情，并补充不同清晰度播放地址 |
| 关闭 | `POST /api/live/rooms/{roomId}/close` | 按 `roomId + userId + status = 'online'` 更新为 `offline` |
| 初始化互动数据 | 创建直播间时 | 删除该新房间残留的弹幕和点赞记录，确保互动数据从 0 开始 |

索引：`idx_live_room_status_created (status, create_time, id)` 用于在线直播间列表排序和分页。

## 三、`live_danmu` 弹幕表

### 表结构

| 字段 | 类型 | 约束/默认值 | 说明 |
| --- | --- | --- | --- |
| `id` | `BIGINT` | 主键、自增 | 弹幕 ID |
| `room_id` | `BIGINT` | `NOT NULL` | 所属直播间 ID，逻辑关联 `live_room.id` |
| `user_id` | `BIGINT` | 可为空 | 发送者用户 ID；身份由认证层传入 |
| `username` | `VARCHAR(50)` | `NOT NULL` | 展示名称；缺省时由服务生成 |
| `content` | `VARCHAR(255)` | `NOT NULL` | 弹幕内容 |
| `color` | `VARCHAR(20)` | `NOT NULL`，默认 `#ffffff` | 弹幕颜色 |
| `send_time` | `TIMESTAMP` | `NOT NULL`，默认当前时间 | 发送时间 |

### 访问关系

| 操作 | 触发接口/代码 | 说明 |
| --- | --- | --- |
| 新增 | WebSocket `/ws/live/{roomId}`，消息 `type = danmu` | 仅直播间在线且参数校验通过时写入 |
| 查询 | `GET /api/live/rooms/{roomId}/danmus` | 按发送时间倒序取最近记录，再按时间正序返回给前端 |
| 清理 | 创建直播间时 | 清理同一直播间的历史互动数据 |

索引：`idx_live_danmu_room_time (room_id, send_time, id)` 用于按直播间查询最新弹幕。

## 四、`room_likes` 点赞表

### 表结构

| 字段 | 类型 | 约束/默认值 | 说明 |
| --- | --- | --- | --- |
| `room_id` | `BIGINT` | 主键 | 所属直播间 ID，逻辑关联 `live_room.id` |
| `like_count` | `BIGINT` | `NOT NULL`，默认 `0` | 当前累计点赞数 |

### 访问关系

| 操作 | 触发接口/代码 | 说明 |
| --- | --- | --- |
| 初始化 | 创建直播间时 | 删除旧记录；查询无记录时按 `0` 返回，首次点赞时自动插入 |
| 累加 | WebSocket `/ws/live/{roomId}`，消息 `type = like` | 使用数据库原子 upsert，将数量加 1 |
| 查询 | `GET /api/live/rooms/{roomId}/like` | 返回当前 `likeCount` |
| 广播 | 点赞成功、新用户连接 | WebSocket 广播最新点赞数 |

当前表记录的是房间总点赞数，没有保存“某个用户是否已经点赞”的明细，因此同一用户重复点赞会重复累计。若产品后续要求“一人一次”，需要新增用户-房间点赞明细表或改造为带用户维度的去重方案。

## 五、跨服务数据边界

| 数据 | 归属 | 直播服务中的处理方式 |
| --- | --- | --- |
| 用户账号、昵称、头像、权限 | 用户/认证服务 | 直播服务只接收认证后的 `X-User-Id`；弹幕展示名目前由请求消息提供或使用默认值 |
| 直播分类信息 | 分类服务或内容服务 | 直播服务只保存 `category_id`，不复制分类详情 |
| SRS 流媒体状态 | SRS 基础设施 | 直播服务通过配置的 SRS API 探活，不把 SRS 内部表当作业务表 |
| 播放页面、推荐、搜索 | 视频/内容或网关服务 | 通过直播服务 API 获取直播间和播放地址 |
| 通知、动态、关注关系 | 互动/社交服务 | 不属于当前直播服务数据库；如需通知，在服务间通过接口或事件传递直播事件 |

## 六、跨服务调用说明

当前直播服务没有直接调用用户服务、分类服务或其他业务微服务，也不共享它们的数据库表。现阶段的外部依赖和失败处理如下：

| 调用方向 | 依赖 | 传递数据 | 调用失败或数据异常时的处理 |
| --- | --- | --- | --- |
| 网关/认证层 -> 直播服务 | 用户身份认证 | 网关在请求头传入 `X-User-Id` | 缺失或不是正整数时，直播服务返回业务码 400；生产环境应由网关先拦截未认证请求 |
| 直播服务 -> SRS | 流媒体 API 探活 | 使用 `LIVE_SRS_API_BASE_URL` 查询版本和流状态 | 探活失败时 `/api/live/srs/health` 返回 `reachable=false`；播放地址仍可返回，避免 SRS 短时故障拖垮直播间查询 |
| 其他业务服务 -> 直播服务 | 直播间、弹幕、点赞信息 | 通过 HTTP API 或 WebSocket 获取 | 直播服务返回统一 `ApiResponse` 业务错误；调用方应检查响应体 `code` 并按需提示或重试，不得改为直读直播数据库 |

用户昵称和分类详情目前不通过同步跨服务调用获取：弹幕展示名由互动消息提供，缺省时由直播服务生成；分类只保存 `categoryId`。如果后续增加用户或分类服务调用，还应补充超时、重试和降级策略，并同步更新接口清单。

## 七、数据一致性原则

1. 直播服务是三张表的唯一写入方，避免多个微服务共享数据库写入。
2. `live_danmu.room_id` 和 `room_likes.room_id` 当前采用逻辑关联，未设置跨表外键，便于微服务独立部署和迁移。
3. 直播间关闭后不删除历史弹幕和点赞记录，历史数据仍可查询；关闭状态下禁止新的弹幕和点赞。
4. 新建直播间时重置互动数据，保证新一轮直播从零开始统计。
5. 生产环境应为数据库配置持久化存储；容器编排示例中的临时存储仅适合课程演示或测试。
