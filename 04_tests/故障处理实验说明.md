# 故障处理实验说明

## 实验目的

验证直播微服务在外部 SRS 故障、依赖探测超时和应用 Pod 重启时的处理行为：请求不因 SRS 探测无限等待，健康接口明确返回降级状态，SRS 恢复后状态回归，Kubernetes Deployment 能自动拉起被删除的 Pod。

## 实验环境与入口

- Kubernetes：GitHub Actions 的一次性 Kind 集群
- 被测服务：`live-service`、`srs`、`frontend`
- 脚本：[`scripts/fault-handling-smoke.sh`](../scripts/fault-handling-smoke.sh)
- CI 入口：`.github/workflows/live-service-ci.yml` 的 `Run fault handling experiment`
- 原始证据：Actions artifact 中的 `hangyin-fault/fault-results.csv` 和每次请求响应 JSON

## 故障场景与判定

| 场景 | 注入动作 | 预期结果 |
| --- | --- | --- |
| 基线 | SRS 正常运行，访问 `/api/live/srs/health` | HTTP 成功且 `data.reachable=true` |
| SRS 下线 | 将 `srs` Deployment 扩容到 0 | live-service 仍可响应，`reachable=false` |
| SRS 恢复 | 将 `srs` 恢复为 1 副本并等待 rollout | `reachable=true` |
| 探测超时 | 临时将 SRS API 指向保留不可路由地址 `192.0.2.1` | 在脚本超时上限内返回 HTTP 成功，`reachable=false`，不阻塞流水线 |
| 应用 Pod 重启 | 删除 live-service Pod | Deployment 自动创建替代 Pod，健康接口恢复 `reachable=true` |

每次探测记录场景、阶段、期望/实际可达状态、HTTP 是否成功、耗时、判定和 UTC 时间戳。任一场景不满足断言，脚本以非零状态退出并由 CI 上传全部诊断文件。

## 实现要点

`SrsHealthService` 使用 1 秒连接超时和 2 秒读取超时。SRS 不可达只影响健康探测结果，不改变已保存的直播间播放地址；上层可以据此重试或提示用户。实验结束时脚本会尽力恢复 SRS 副本数，Kind 集群随后销毁，不会污染本地环境。
