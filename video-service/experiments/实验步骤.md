## 实验一: 自动扩缩容 (HPA)

### 前置条件
- [x] Docker Desktop Kubernetes 已启用
- [x] metrics-server 已安装且 `kubectl top nodes` 有输出
- [x] video-service 已部署, Pod 全部 Running
- [x] HPA 已创建, TARGETS 显示具体百分比

### 步骤

#### 1. 修复 kubeconfig (如有 TLS 报错)

```powershell
kubectl config set-cluster docker-desktop --server=https://kubernetes.docker.internal:6443 --insecure-skip-tls-verify=true
```

#### 2. 安装 metrics-server

```powershell
# 下载 YAML
Invoke-WebRequest -Uri "https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml" -OutFile metrics.yaml

# 部署
kubectl apply -f metrics.yaml

# 打补丁 (Docker Desktop 的 kubelet 用自签名证书, 需要跳过验证)
kubectl patch deployment metrics-server -n kube-system --type=strategic --patch-file metrics-patch.yaml

# 等 1 分钟, 验证
kubectl get pods -n kube-system | findstr metrics
kubectl top nodes
```

看到 CPU 和 MEMORY 输出即成功。

#### 3. 构建镜像并部署 video-service

```powershell
# 构建镜像 (Docker Desktop 的 K8s 会直接使用本地镜像)
cd video-service
docker build -t ghcr.io/ve1bae/demo-video-service:latest .
cd ..

# 部署
kubectl apply -f video-service/k8s/

# 等待 Pod 就绪
kubectl -n video-service get pods -w
# 等 Pod 全部 1/1 Running 后按 Ctrl+C
```

#### 4. 创建 HPA

```powershell
kubectl apply -f video-service/k8s/05-hpa.yaml

# 等 1-2 分钟让 metrics-server 采集指标
kubectl -n video-service get hpa
# TARGETS 应显示具体数字 (如 3%/50%), 不是 <unknown>
```

#### 5. 端口转发 (终端 1, 保持不关)

```powershell
kubectl -n video-service port-forward svc/video-service 18082:8082
```

#### 6. 验证接口 (终端 2, 新开窗口)

```powershell
curl.exe http://localhost:18082/actuator/health
curl.exe http://localhost:18082/api/videos/recommend
```

health 返回 `"status":"UP"`, recommend 返回 `{"code":200,...}` 即正常。

#### 7. 记录基线 (终端 2)

```powershell
kubectl -n video-service get hpa
kubectl -n video-service get pods
kubectl -n video-service top pods
```

记录: Pod 数=2, CPU 百分比。

#### 8. 启动压测 (终端 2)

```powershell
cd d:\二下\软工\demo
.\stress-test.ps1 -Url http://localhost:18082/api/videos/recommend -Concurrency 200 -DurationSeconds 120
```

#### 9. 观察扩容 (终端 3, 新开窗口)

```powershell
kubectl -n video-service get hpa -w
```

再开终端 4:

```powershell
kubectl -n video-service get pods -w
```

**预期现象:** 压测开始后 CPU 利用率上升超过 50%, HPA 扩容, Pod 从 2 增加到 4-6 个。

#### 10. 压测中记录数据

每 30 秒在终端 3 或 4 执行:

```powershell
kubectl -n video-service get hpa
kubectl -n video-service top pods
```

压测结束后脚本输出: 吞吐量(req/s)、错误数、错误率。

#### 11. 观察缩容

压测结束后等 3-5 分钟:

```powershell
kubectl -n video-service get pods -w
```

**预期现象:** CPU 下降, HPA 缩容, Pod 从 6 缩回 2。

| 阶段 | Pod 数 | CPU% | 吞吐量(req/s) | 错误数 | 错误率 |

| 压测第 30 秒 | | | | | |

## 实验二: 故障处理 (超时返回 + 备用结果)

### 原理

video-service 的 `FaultTestController` 提供 `GET /api/videos/{videoId}/author-info` 接口,
内部通过 `UserServiceClient` 调用 user-service 取作者昵称:

- user-service 正常 → 返回真实昵称, `fallback=false`
- user-service 宕机/超时 → 3 秒超时后返回备用结果 "匿名用户", `fallback=true`
- video-service 不崩溃, 其他接口不受影响

### 步骤

#### 1. 调用接口 (user-service 未部署, 自动走超时+降级)

```powershell
curl.exe http://localhost:18082/api/videos/1/author-info
```

因为 user-service 没有部署, `UserServiceClient` 连接失败, 3 秒超时后返回:

```json
{"code":200,"data":{"videoId":1,"title":"...","authorId":1,"nickname":"匿名用户","fallback":true}}
```

记录响应时间 (约 3 秒) 和 `fallback=true`。

#### 2. 验证 video-service 没有崩溃

```powershell
kubectl -n video-service get pods
# Pod 仍然 1/1 Running, 没有 Restart

curl.exe http://localhost:18082/api/videos/recommend
# 接口正常返回, 不受影响
```

#### 3. (可选) 部署一个简单的 user-service 模拟正常场景

如果需要演示"正常 → 故障 → 恢复"完整流程, 可以部署一个假的 user-service:

```powershell
# 启动一个简单 HTTP 服务模拟 user-service (端口 8081)
# 可以用 Python: python -m http.server 8081
# 或用 Docker: docker run -d -p 8081:80 nginx
```

然后修改 video-service 的 `user-service.base-url` 指向它, 重启 video-service, 观察 `fallback=false` (正常) → 停止假服务 → `fallback=true` (降级)。

### 记录表格

| 场景 | 响应时间 | HTTP 状态 | 返回昵称 | fallback | video-service 是否崩溃 |
|------|---------|-----------|---------|----------|----------------------|
| user-service 不可用 | ~3s (超时) | 200 | 匿名用户 | true | 否 |
| user-service 正常 | <100ms | 200 | 真实昵称 | false | 否 |
| 恢复后再次调用 | <100ms | 200 | 真实昵称 | false | 否 |

## 实验三: 对比改造前后的性能

### 前置条件
- 单体版本 (backend/) 和微服务版本 (video-service/) 使用同一台机器
- 同一批测试数据 (video 表有 id=1 的记录)
- 同一份压测脚本 (d:\二下\软工\demo\stress-test.ps1)

### 测试接口 (3 个)

| # | 接口 | 说明 |
|---|------|------|
| 1 | GET /api/videos/recommend | 推荐流, 无参数, 纯读 |
| 2 | GET /api/videos/1 | 视频详情, 单条查询 |
| 3 | GET /api/videos/1/comments?page=1&pageSize=20 | 评论列表, 分页查询 |

### 步骤

#### 1. 启动单体版本 (backend, 端口 9090)

```powershell
cd backend
./mvnw.cmd spring-boot:run
# 等待 "Started DemoApplication"
```

#### 2. 压测单体版本 (3 轮 x 3 接口)

新开终端:

```powershell
cd d:\二下\软工\demo

# 接口 1: recommend
.\stress-test.ps1 -Url http://localhost:9090/api/videos/recommend -Concurrency 100 -DurationSeconds 60
# 重复 3 次

# 接口 2: video detail
.\stress-test.ps1 -Url http://localhost:9090/api/videos/1 -Concurrency 100 -DurationSeconds 60
# 重复 3 次

# 接口 3: comments
.\stress-test.ps1 -Url "http://localhost:9090/api/videos/1/comments?page=1&pageSize=20" -Concurrency 100 -DurationSeconds 60
# 重复 3 次
```

每次记录脚本输出的吞吐量和错误率。压测中记录 CPU 和内存:

```powershell
curl.exe http://localhost:9090/actuator/metrics/system.cpu.usage
curl.exe http://localhost:9090/actuator/metrics/jvm.memory.used
```

#### 3. 停止单体版本, 启动微服务版本 (端口 8082)

停掉 backend (Ctrl+C), 然后:

```powershell
cd video-service
./mvnw.cmd spring-boot:run
# 等待 "Started VideoServiceApplication"
```

#### 4. 压测微服务版本 (3 轮 x 3 接口)

新开终端:

```powershell
cd d:\二下\软工\demo

# 接口 1: recommend
.\stress-test.ps1 -Url http://localhost:8082/api/videos/recommend -Concurrency 100 -DurationSeconds 60
# 重复 3 次

# 接口 2: video detail
.\stress-test.ps1 -Url http://localhost:8082/api/videos/1 -Concurrency 100 -DurationSeconds 60
# 重复 3 次

# 接口 3: comments
.\stress-test.ps1 -Url "http://localhost:8082/api/videos/1/comments?page=1&pageSize=20" -Concurrency 100 -DurationSeconds 60
# 重复 3 次
```

### 差异解释要点

- 微服务可能更慢: 多了网络跳转、序列化开销

- 必须如实记录, 只有确实测出来更快才能写"性能提升"
