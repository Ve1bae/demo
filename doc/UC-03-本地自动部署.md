# UC-03 本地自动部署

目标：复用现有 `Helium-DockerDesktop` runner，更新 `docker-desktop` 上 `hangyin` 命名空间中的三个微服务及前端，不重新注册 runner。

## 触发及安全边界

- 新任务位于 `uc03-microservices-cicd.yml` 的 `deploy-local`。
- 仅 `Ve1bae/demo` 仓库所有者向 `feature/uc03-microservice-delivery` 分支 push 可触发；PR 和其他分支不触发。
- 必须先通过 integration、镜像发布和云端 Kind 部署实验。
- 沿用旧工作流的 `[self-hosted, Windows, X64]` 标签；检出代码之前校验 `RUNNER_NAME` 必须精确为 `Helium-DockerDesktop`。名称不是标签；若有多个同标签 runner，请在 GitHub 分配唯一标签并更新 runs-on。
- 与旧单体工作流共享部署互斥组，不取消已经开始的部署。旧单体本地任务也已限制为所有者 push，不执行 PR。
- 公开仓库的持久 runner 仍有风险：这些条件不是安全沙箱，能修改可信分支工作流的人仍可在电脑执行命令。应限制仓库写权限，长期使用宜迁移至隔离机器或私有部署仓库。

## 部署行为

`scripts/deploy-local-apps.ps1` 只适用于已经初始化的本地集群。固定使用 `--context docker-desktop`，不改变用户默认上下文。

1. 核对现有应用、网关 NodePort、数据库、MinIO 和 SRS 就绪状态。
2. 验证推荐、直播、网关及 MinIO API 健康；基线不健康就停止，不更新应用。
3. 从通过云端验证的提交本地构建四个镜像，标签使用完整提交 SHA；前端按现有网关 NodePort 构建。此处是同提交本地重建，不是直接部署 GHCR 中的相同镜像摘要。
4. 逐个更新应用镜像并等待就绪，再运行 API 健康检查。
5. 更新失败时尝试恢复本次已改动应用原有的镜像；回滚失败会明确警告，整个任务保持失败。

不应用数据库清单、不重建 Secret、不做数据迁移、不删卷、不清理旧镜像、不在本机做 HPA 压力或故障注入。基础设施、环境变量、网关配置的变更需单独审核部署；本任务不自动同步这些内容。

本机当前数据库使用临时存储、未发现 PVC。更新应用不会主动改动数据库 Pod，但不能承诺数据库在重启、重建或节点故障时保留数据。持久化迁移需要先备份，不能直接重新套用初始化部署脚本。

## 验证与启用

只读预检（不会构建或部署；rollout status 仅观察状态）：

```powershell
.\scripts\deploy-local-apps.ps1 -ImageTag (git rev-parse HEAD) -PlanOnly
```

配置需提交并推送后才会被 GitHub 执行；本地编辑不代表已启用。runner 必须在线并可访问 Docker、kubectl、PowerShell 和依赖镜像源。电脑关机、休眠或 runner 退出时，任务不会自动在本机执行。

本次核查确认 `C:\actions-runner\.runner` 的注册名称及仓库，但 API 查询 runner 列表返回 403，未能独立确认实时在线状态和自定义标签。不要在对话、文档或仓库中保存 runner 注册 Token、`.credentials` 或数据库密码。
