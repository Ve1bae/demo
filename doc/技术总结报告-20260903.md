# 《航音视频》软件工程基础实践技术总结报告

## 1. 项目概况

本项目沿用上学期《航音视频》系统，在保留原单体基线的前提下，将后端拆分为 `user-service`、`video-service` 和 `live-service` 三个业务微服务，并通过 Nginx API 网关向前端提供统一入口。当前整合分支为 `microservice`，改造前基线由 `monolith-start` 标签保留。

## 2. 完成内容

- `user-service` 负责账户、资料、关注和用户兴趣偏好。
- `video-service` 负责视频上传、MinIO 对象存储、视频播放、推荐排序、观看历史、点赞收藏、评论和点播弹幕。
- `live-service` 负责直播间生命周期、SRS 地址适配、直播弹幕和直播点赞。
- 三个服务分别拥有自己的数据库表，通过 HTTP 或 WebSocket 协作，不跨服务直接查询业务表。
- 推荐逻辑包含热度、时间、关注作者、兴趣标签和观看历史降权，并在 user-service 不可用时降级为公共热度排序。

## 3. 工程化与云原生实践

项目提交了服务 Dockerfile、数据库初始化脚本、Compose 编排、GitHub Actions、Kubernetes 清单、健康探针、HPA 和部署脚本。已保存的本地证据包括 Compose 联调、Kubernetes rollout、HPA `1 -> 2 -> 3 -> 1` 扩缩容和 user-service 停止后的推荐降级恢复。

## 4. 测试与性能结果

三个服务 Maven 测试合计 `51/51` 通过；当前工作区还保存了真实 HTTP/API 和 Playwright 回归材料。单体版和微服务版使用同一台机器、同一批测试数据、同一并发梯度和同一脚本，各重复 3 次，错误率均为 0%。微服务在视频详情和评论列表的高并发档位、播放计数接口的主要测量档位表现较好，但结果只代表本机和当前数据规模，不作普遍生产性能结论。

## 5. 主要技术难点与处理

### 5.1 跨服务偏好读取

视频服务不再读取用户服务数据库，而是通过 `HttpUserPreferenceClient` 请求 `/api/users/{userId}/preferences`。调用超时、服务停止或响应无法解析时返回空偏好，保证推荐接口仍能返回公开视频。

### 5.2 微服务环境中的数据初始化

用户、视频和直播数据库分别初始化，推荐测试数据和浏览器 E2E 数据使用独立 SQL 脚本注入。Compose 与 Kubernetes 均使用环境变量、Secret 或 ConfigMap 传递运行配置，仓库不保存真实口令。

### 5.3 真实测试与本机环境限制

测试不以 Mock 或截图代替真实结果。当前 SRS 浏览器专项需要 FFmpeg 推流，本机未找到可执行的 `ffmpeg.exe`，因此该专项必须在安装 FFmpeg 的本机或 CI runner 上重新运行。该限制已在测试报告和验收矩阵中保留。

## 6. AI 工具使用与人工复核

本项目使用生成式 AI 辅助梳理需求与服务边界、生成测试用例初稿、排查 Docker/Kubernetes/CI 配置问题和整理文档。所有进入仓库的代码均经过人工阅读、编译、测试和运行结果核对；测试报告只记录实际执行结果，未将脚本存在或历史运行结果冒充当前版本通过。

提交前由组员完成以下人工复核：

- 检查差异文件，排除 `target/`、浏览器报告和本地凭据。
- 在可用 Docker 环境重新运行 Compose smoke、浏览器 E2E、故障演练和 HPA。
- 在当前提交 push 后检查 Actions 的真实日志、Artifact 和部署结果。
- 导出需求、概要设计、详细设计和 UML 模型的可读 PDF。

## 7. 尚需由小组补齐的材料

当前报告仍需由组内填写项目管理平台地址、每日站会简报、每日看板截图、最终答辩 PPT、成员姓名/分工、个人权重和全员确认记录。SRS 浏览器播放专项的最终结果也必须以可执行 FFmpeg 环境中的真实运行记录为准。

## 8. 结论

当前 `microservice` 工作区已经具备可运行的三服务实现和主要工程化验收证据。完成第 7 节列出的真实材料并复验 SRS/当前提交 CI 后，才可以提交“全部任务完成”的最终版本。
